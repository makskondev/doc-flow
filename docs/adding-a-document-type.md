# Как добавить тип документа, шаг или ожидание

Всё делается в проекте `src/DocFlow.Documents`. Маршруты, шаги и сканеры подхватываются автоматически
(`AddDocFlowFlows`) — регистрировать вручную ничего не нужно. Опечатки в маршрутах ловит валидатор при старте.

## Новый тип документа

1. Константа в `DocumentTypes.cs`.
2. Папка `DocFlow.Documents/<Тип>/` и в ней маршрут:

   ```csharp
   public sealed class ContractRoute : IRoute
   {
       public string Key => DocumentTypes.Contract;
       public int Version => 1;                       // увеличивайте при изменении состава узлов

       // Как распознать документ этого типа: источник, колонки вьюхи, каталог, маска файла
       public bool Matches(DocumentCandidate c)
           => c.SourceId == SourceIds.View2 && c.Get(DataKeys.DocKind) == "contract";

       public void Build(IRouteBuilder r) => r
           .Step<IntakeStep>()
           .Step<AutoSignStep>()
           .Include(RouteFragments.Finish);           // проверка → подпись и отметка в БД → конечный каталог
   }
   ```

   **Правило `Matches` — часть заведения типа.** Документу должен подходить ровно один маршрут: после добавления нового
   проверьте, что правила не пересекаются (пример теста — `tests/.../Documents/RouteMatchingTests.cs`).
3. Каталоги типа — в `appsettings.json`, секция `Storage:Types:<тип>` (`SignInputDir`, `SignResultDir`, `FinalDir`, `SearchDir` —
   только нужные маршруту). Каталог не настроен — шаг упадёт с понятной причиной и документ уйдёт в эскалацию.
4. Шаги, которые нужны только этому типу, кладите рядом с маршрутом; общие — в `Common/Steps/`.
5. Если нужны колонки вьюхи для штампа и т.п. — объявите `RequiredData` (имена — в `DataKeys.cs`).
6. Откуда приходят документы:
   * **из вьюхи** — если вьюхи ещё нет в `Documents/Views`, добавьте описание по образцу `View1Reader` (уникальный `SourceId`
     из `SourceIds`, `ReadAsync`). Если вьюха уже есть, достаточно убедиться, что нужные для правила колонки попадают в `Data`;
   * **из каталога** — добавьте каталог в `Intake:Directories` (`Name`, `Path`, `Mask`) и опирайтесь в правиле на
     `SourceDirectory` / `FileName`.
7. Тест: сквозные примеры по всем сценариям — `tests/DocFlow.Tests/Documents/ScenarioTests.cs` (`ScenarioHarness`).

## Новый шаг

```csharp
public sealed class MyStep(IFileStorage fs, IOptions<StorageOptions> storage) : IStep
{
    public async Task ExecuteAsync(StepContext ctx, CancellationToken ct)
    {
        var name = ctx.RequireData(DataKeys.FullName);        // входные данные документа (только чтение)
        ...
        ctx.Bag[BagKeys.PdfPath] = path;                      // данные для следующих шагов
    }
}
```

Правила шага:

* **Идемпотентность.** После сбоя шаг выполнится заново с начала. Повтор не должен дублировать эффект
  (проверяйте «уже сделано», пишите в детерминированные пути, штампуйте из сохранённого оригинала).
* **Ошибки.** Обычное исключение — временный сбой: повторы с backoff, затем эскалация. `PermanentStepException` — повторять
  бессмысленно (невалидная подпись, нет обязательного поля): сразу эскалация оператору.
* **Файлы** — только через `IFileStorage`, запись атомарная (`WriteAtomicAsync`).
* **Данные.** `ctx.Data` — вход из источника, `ctx.Bag` — рабочие данные шагов. Не кладите в `Bag` то, что нельзя хранить в БД.
* **Внешние системы** — через интерфейсы из `Integrations/`; реализации лежат в `DocFlow.Host`.

## Новое ожидание внешнего события

1. Сигнал: константа в `Signals.cs`.
2. В маршруте: `.WaitFor(Signals.MySignal, TimeSpan.FromDays(3))` (не может быть последним узлом).
3. Источник сигнала: класс `ISignalSource` (пример — `Common/SigningResultScanner.cs`): находит событие и вызывает
   `engine.SignalAsync(processId, signal, ct)`. Без него валидатор не даст сервису стартовать.
4. Истёк таймаут → эскалация (письмо + оператор), отдельно обрабатывать не нужно.

## Если данные придётся подгружать шагом (БД, внешний API)

Например, для документов из каталога, у которых нет данных для штампа. Нужно:

1. Добавить в `StepContext` метод `SetData(key, value) => Process.Data[key] = value` и поправить комментарий к `Data`.
2. Шаг перед штампом: если данные уже есть (пришли из вьюхи или загружены прошлой попыткой) — выйти; иначе загрузить
   и записать через `SetData`; «записи нет» — `PermanentStepException`, сбой API — обычное исключение.
3. Убрать `RequiredData` у маршрута, если он должен принимать и документы без данных (проверка при регистрации иначе не пустит),
   либо завести отдельный тип документа с отдельным маршрутом.

## Что не нужно трогать

`DocFlow.Engine` не знает ни о документах, ни о подписях. Если для нового типа документа кажется, что нужно править движок,
обычно это признак недостающей возможности шага или маршрута — обсудите прежде, чем менять.

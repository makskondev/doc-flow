# Архитектура

## Общая схема

```
Источники документов ──► Регистратор ──► Процесс (PostgreSQL) ◄── Раннер выполняет узлы маршрута
 • каталоги (по маске)   определяет тип    RouteKey = тип       • шаг: идемпотентная работа
 • вьюхи сторонней БД    (IRoute.Matches), документа            • ожидание: ждёт сигнала
                                                                • сбой → повторы → эскалация
Сканеры сигналов (файлы подписи) ──► будят процессы, ждущие сигнал
```

Три фоновых воркера (`Engine/Workers`): `IntakeWorker` (опрос источников и регистрация), `SignalScanWorker`
(сканеры сигналов), `ProcessRunnerWorker` (единственный исполнитель шагов; также таймауты и досылка писем).

## Основные понятия

* **Маршрут** (`IRoute`) — класс в одном файле: `Step<T>()`, `WaitFor(signal, timeout)`, `Include(fragment)`.
  Ключ маршрута = тип документа (`report`, `zop`).
* **Шаг** (`IStep`) — идемпотентная единица работы. Ошибка = исключение (повторы с backoff),
  `PermanentStepException` = сразу эскалация.
* **Процесс** (`DocumentProcess`) — один прогон обработки документа. Курсор хранится как **id узла**, а не индекс:
  правка маршрута не ломает живые процессы.
* **Статусы:** `Running`, `Waiting`, `NeedsAttention`, `Completed`, `Cancelled`.
* **Валидатор маршрутов** при старте: шаги зарегистрированы, у каждого ожидания есть сканер,
  последний узел — не ожидание.

## Маршруты (четыре сценария постановки)

| Сценарий | Тип | Откуда | Шаги |
|---|---|---|---|
| 1 | `zop` | view_1, `DocKind = zop` | Intake → ApplyStamp → SendToSignature (файл **перекладывается** в папку для подписи) → **ждём файл и подпись в директории результата подписания** (7 дней) → Verify → Persist → MoveToFinal |
| 2 | `report` | view_2 | Intake → AutoSign (REST) → Verify → Persist → MoveToFinal |
| 3 | `inbox` | каталог `inbox`, маска `*.pdf` | Intake → RegisterInExternalDb → AutoSign (REST) → Verify → Persist → MoveToFinal |
| 4 | `archive` | view_1, `DocKind = archive` | FindFile → MarkProcessed → MoveToFinal |

Общий хвост сценариев с подписью (`RouteFragments.Finish`): **Verify → Persist → MoveToFinal**.

* **Persist («подпись в БД»)** — сохраняет подпись во внешней БД и ставит отметку «подписан» одной операцией; после неё
  запись исчезает из вьюхи. Для маршрутов без подписи (сценарий 4) то же делает **MarkProcessed**: только отметка.
* **MoveToFinal** идёт после записи в БД, как в постановке. Файл сохраняет исходное имя, подпись получает имя
  «имя.pdf.sig».
* Названия типов и значения `DocKind` — примеры: переименуйте под свои.

## Источники документов и тип документа

* **Тип документа определяет маршрут, а не источник.** Каждый маршрут (`IRoute`) содержит правило `Matches(DocumentCandidate)`,
  которое пишет разработчик при заведении маршрута: источник, значения колонок вьюхи, каталог, маска имени файла.
  Регистратор находит маршрут, правило которого подошло.
* **Документу должен подходить ровно один маршрут.** Ни одного — документ не регистрируется (запись остаётся в источнике,
  в лог один раз пишется предупреждение). Больше одного — ошибка конфигурации, документ не регистрируется, в лог пишется
  ошибка. Ошибка внутри правила не останавливает остальные документы пачки.
* **Одна вьюха может отдавать документы разных типов** (view_1: сценарии 1 и 4) — тогда тип различает колонка, и она должна
  попасть в `Data`. Вьюх может быть несколько.
* **Вьюха описывается классом** `IPendingDocumentsReader` в `Documents/Views` (образцы — `View1Reader`, `View2Reader`):
  `SourceId` и `ReadAsync` (SELECT: id, путь к файлу — необязателен, колонки в `Data`). Для каждого такого класса
  автоматически создаётся источник документов.
* **`SourceId` должен быть уникальным:** он входит в ключ дедупликации `(SourceId, ExternalId, Run)`. У разных вьюх
  идентификаторы документов могут совпадать. Дубль `SourceId` валидатор обнаруживает при старте, и сервис не запускается.
* **Каталоги** (`Intake:Directories`: `Name`, `Path`, `Mask`): `SourceId = "dir"`, идентификатор документа — `{Name}/{имя файла}`
  (файлы с одинаковыми именами в разных каталогах не конфликтуют); атрибуты `SourceDirectory` и `FileName` попадают в `Data`.
  Тип «по каталогу» — сравнение `SourceDirectory`, «по маске» — `FileMask.IsMatch(...)` в правиле `Matches`.
* **Путь к файлу необязателен.** Если вьюха его не отдаёт (сценарий 4), файл находит шаг `FindFileStep`.

## Регистрация документов

* Уникальность: `(SourceId, ExternalId, Run)`; пока есть активный процесс, повторы из источника игнорируются.
* Запись вернулась во вьюху после `Completed` (в сторонней БД зачистили подпись) = новый `Run`.
  Защита от устаревшего снимка: `CompletedAt < момент начала опроса`.
* `Cancelled` автоматически **не** перезапускается (запись всё ещё во вьюхе); только `POST /processes/{id}/restart`.

## Входные данные документа (`Data`)

Вместе со списком документов источник может отдавать дополнительные данные — например, поля для штампа
(ФИО, даты, номер соглашения):

```
колонки вьюхи → PendingDocument.Data → DocumentCandidate.Data → DocumentProcess.Data → шаг: ctx.Data / ctx.RequireData("...")
```

* `Data` — **снимок на момент регистрации**; для своих промежуточных данных у шагов есть `Bag`.
  Значения — строки (даты — ISO 8601, числа — `InvariantCulture`); преобразуйте колонки так в `IPendingDocumentsReader`.
* Маршрут объявляет обязательные поля: `IRoute.RequiredData` (пример — `ZopRoute`, имена — `DataKeys`).
  Документ с неполными данными **процесс не создаёт**: запись остаётся во вьюхе, в лог один раз пишется предупреждение.
* `ctx.RequireData(key)` в шаге: нет поля = `PermanentStepException`.
* Повторная обработка (`Run` + 1) получает свежий снимок. `restart` после `Cancelled` берёт данные **прежнего прогона**.
* Если данные придётся подгружать отдельным шагом (БД, внешний API) — см. `docs/adding-a-document-type.md`.
* ⚠️ ФИО и подобное — персональные данные: лежат в `processes` и отдаются операторским API.

## Файлы и каталоги

Каталоги задаются **по типам документов** (`Storage:Types:{тип}`), нужны только те, что использует маршрут:

| Каталог | Назначение |
|---|---|
| `SignInputDir` | «папка для проставления подписи»: сюда `SendToSignatureStep` **перекладывает** файл как `{processId}.pdf` |
| `SignResultDir` | «директория результата подписания»: здесь должны появиться `{processId}.pdf` и `{processId}.sig` |
| `FinalDir` | конечный каталог |
| `SearchDir` | где `FindFileStep` ищет файл, если источник не передал путь |

* Рабочие копии: `{WorkingDir}/{processId}.pdf|.orig.pdf|.sig`; в конце они удаляются.
* Сканер результата подписания (`SigningResultScanner`) считает результат готовым, когда **и файл, и подпись** есть и не менялись
  (размер и время записи) между двумя сканами. Система подписания должна сохранять имена `{processId}.pdf` / `{processId}.sig`.
* В конечный каталог файл ложится под исходным именем (подпись — «имя.pdf.sig»). Если там уже есть **другой** файл с таким
  именем, шаг не перезаписывает его: эскалация оператору. Тот же файл (недозавершённый прошлый перенос) — источник просто удаляется.
* Исходный файл на чужой шаре не удаляется: `IntakeStep` его копирует. Каталоговый источник после копирования переносит оригинал в `_processed`.
* Все записи атомарны (`.tmp` + переименование); перенос безопасен к повтору (`MoveIdempotentAsync`).

## Внешняя БД

Везде, где говорится о «БД» документов, — это **сторонняя БД**, а не внутренняя PostgreSQL сервиса. Контракт `IExternalDocumentDb`:

* `RegisterDocumentAsync(processId, info)` — сценарий 3: сохранить информацию о файле, вернуть идентификатор записи.
  Идемпотентно по `processId`. Идентификатор запоминается (`Bag`) и используется дальше вместо `ExternalId`.
* `IsCompletedAsync(id)` / `CompleteAsync(id, signature?)` — подпись (если есть) и отметка одной операцией; после неё запись
  исчезает из вьюхи. Шаги проверяют `IsCompletedAsync`, поэтому повтор безопасен.

## Эскалация

Таймаут ожидания или исчерпанные повторы → статус `NeedsAttention`, письмо (`IEscalationNotifier`), дальше оператор:
`retry` / `continue` / `cancel` / `restart` (см. `docs/operations.md`). Подпись, пришедшую после таймаута, обрабатывает
`retry` на узле ожидания: процесс снова ждёт, сканер сразу находит файл.

## Хранилище: PostgreSQL + EF Core (`DocFlow.Data`)

* Таблицы: `processes` (процесс целиком; `Bag` и `Data` — JSON в `text`, статус — строкой) и `process_events` (аудит).
* **Optimistic lock:** `Version` — токен конкурентности; `SaveAsync` делает `UPDATE ... WHERE "Version" = <ожидаемая>`,
  при расхождении бросает `ConcurrencyException`.
* **Уникальность в БД** (страховка от гонок регистрации): `ux_processes_document_run` — `(SourceId, ExternalId, Run)`;
  `ux_processes_active_document` — частичный индекс: не более одного активного процесса на документ.
  `TryAddAsync` превращает нарушение уникальности (SQLSTATE 23505) в `false`.
* Репозиторий — singleton, на каждую операцию свой короткий `DbContext`; процессы возвращаются без трекинга.
* Раннер берёт готовые процессы пачками по 500 (самые старые первыми).
* Аудит пишется синхронно одной вставкой; сбой записи аудита логируется и не прерывает обработку документа.
* Колонки именуются как свойства (`"Status"`, `"NextAttemptAt"`…); если нужен snake_case — подключите
  `EFCore.NamingConventions` и обновите фильтр частичного индекса в `DocFlowDbContext`.
